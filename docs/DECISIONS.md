## Expense and settlement rules

- **Status: implemented in the client; trusted cross-account attribution is not verified.** A new expense stores `createdByUserId` from the signed-in account ID; editing preserves its original value. Show the creator by resolving that account ID through the group's `memberAccounts` map and member list. Legacy records and missing/unlinked mappings show “등록자 정보 없음”. This uses the existing local group snapshot; it adds no expense write API or database migration and does not establish cross-account synchronization.
- **Status: decided.** Split each expense equally among the participants selected for that expense. Custom per-person amounts are outside this first expense flow.
- **Status: decided.** The expense form offers quick title buttons for `점심 식사`, `저녁 식사`, `숙소비`, `교통비`, and `카페·간식`. Selecting one fills the editable expense title; amount, payer, and participants remain separately chosen.
- **Status: decided.** The payer is selected independently from the expense participants, so a trip member can pay on behalf of people who share that expense.
- **Status: decided.** Store and calculate amounts in whole Korean won. Divide evenly, then distribute remaining one-won units to selected participants in the group's saved member order.
- **Status: decided.** Recalculate the settlement from the current expense list after an expense or participant change; do not keep displaying a result based on stale inputs.
- **Status: decided.** Users can edit or delete an existing expense from the trip detail. Editing keeps the expense's identity and updates its title, amount, payer, and participants; deletion requires confirmation. Both changes immediately recalculate settlement from the remaining current expenses. A settled trip must be reopened before expenses can be changed.
- **Status: decided.** If several transfer plans use the same minimum number of transfers, show one deterministic plan using the group's saved member order.
- **Status: decided.** Viewing the calculated transfer plan does not mark a trip settled. After transfers are actually complete, the user marks that trip as settled; the app stores the completion time and blocks new expenses. The user can reopen settlement to correct the trip, which enables expense entry and recalculates the plan.
- **Status: decided; server implementation pending.** The treasurer can send a settlement request to linked trip members. Members who owe money mark their transfers complete; when every required transfer is marked complete, the trip becomes settled automatically. The app does not verify bank transfers. Delivering requests to other devices requires member accounts, shared server data, and push-notification delivery; local-only storage cannot notify other members.

## Trip sync retry safety

- **Status: decided; domain contract implemented, UI integration pending.** Only expense and settlement command RPCs may expose `safeToResend`, and only with the original command ID. A retry must repeat the exact action, entity, payload, expected version, actor, and idempotency key. The RPC stores the request hash and result by `(actor_user_id, idempotency_key)` and returns the stored result for an identical successful request; a changed request with the same key is rejected. Photo flows include separate Storage operations and are not marked safe for whole-operation replay. A refreshed snapshot reconciles entity state but does not identify a specific command result. ## Group activity history MVP

- **Status: implemented locally; audit migrations applied to `myg`; trip-detail feed visually verified on Android emulator; live authorization not fully device-tested.** The activity view reads only supported `group_sync_events` trip-change actions; it does not infer group lifecycle events or reconstruct prior history from recipient notifications. Allowed action mappings are `photo.upsert` → `photo_added`, `photo.set_cover` → `photo_cover_changed`, `photo.delete` → `photo_removed`, `expense.create/update/delete` → `expense_added/updated/removed`, and `settlement.complete/reopen` → `settlement_completed/reopened`. Return only event ID, mapped type, UTC occurrence time, database group ID, trip client ID, and an active member `{id, displayName}` actor or `null`.
