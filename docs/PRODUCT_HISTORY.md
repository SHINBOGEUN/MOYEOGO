# Product and request history

이 문서는 사용자가 어떤 문제를 해결하려 했는지, 요청을 통해 제품과 화면이 어떻게 정리됐는지, 그리고 그 이유가 무엇인지 보존한다. 현재 승인된 동작은 [`PRODUCT_GOAL_V1.md`](PRODUCT_GOAL_V1.md)와 [`DECISIONS.md`](DECISIONS.md)를 기준으로 한다. 이 기록은 그 결정을 대신하지 않는다.

> 대화 원문에는 각 요청의 날짜가 일관되게 남아 있지 않아, 아래 항목은 날짜를 추측하지 않고 요청이 나온 순서로 정리했다. 이 문서의 첫 정리일은 2026-10-09이다.

## 요청에서 현재 방향까지

### 1. 친구들과 실제로 쓸 국내 여행 앱을 먼저 만들기

- **요청:** 처음부터 불특정 다수의 멤버를 모으는 플랫폼보다, 사용자가 자기 친구들과 사용할 앱을 먼저 만들고 싶다고 했다.
- **이유:** 초기 사용자가 직접 반복해서 쓸 흐름을 먼저 검증하고, 공개 모집과 커뮤니티는 나중에 다루려는 목적이다.
- **결과:** 첫 목표를 여러 친구 모임, 국내 여행, 지출 분담과 정산, 사진과 위치 기반 추억 지도에 집중했다. 공개 모임 모집, 커뮤니티, 해외여행은 첫 목표에서 제외했다.
- **현재 기준:** [`PRODUCT_GOAL_V1.md`](PRODUCT_GOAL_V1.md), [`DECISIONS.md`](DECISIONS.md)의 제품 범위.

### 2. 모임마다 여행과 지출을 나누고 마지막에 정산하기

- **요청:** 여러 모임을 만들고, 모임 안에 여행을 만들어 총무를 정한다. 결제마다 실제로 나눌 사람을 다르게 고르고, 여행 마지막에 누가 누구에게 얼마를 보내야 하는지 보여주길 원했다.
- **이유:** 총액만 인원수로 나누면 일부 지출에 참여하지 않은 친구에게도 비용이 배분될 수 있어, 지출별 분담자를 기록해야 한다.
- **결과:** 결제자와 분담자를 별도 지정하고, 지출 참여자끼리 균등 분할하며, 남는 1원은 모임 멤버 순서대로 나누고, 송금 횟수를 줄이는 결과를 선택했다. 같은 최소 송금 수의 결과가 여러 개면 멤버 순서로 하나를 고른다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Expense and settlement rules.

### 3. 여행 사진을 위치에 쌓고 대표 사진을 지도 추억으로 표현하기

- **요청:** 국내 여행 중 찍은 사진을 모임방에 공유하고, 사진의 위도·경도로 지도에 쌓고 싶다고 했다. 사진 하나를 골라 3D 애니메이션 느낌으로 지도에 올리는 아이디어도 1차 목표에 포함했다.
- **이유:** 정산으로 여행 비용을 정리하는 데 그치지 않고, 다녀온 장소와 사진을 여행의 기록으로 남기려는 목적이다.
- **결과:** 위치가 있는 사진을 여행 지도에 표시하고, 대표 사진의 3D 스타일 표현을 검증하는 것을 장기적인 첫 목표에 넣었다. 지도 제공자, 사진이 GPS 정보를 갖지 않은 경우의 처리, 구체적인 3D 표현은 아직 결정하지 않았다.
- **현재 기준:** [`PRODUCT_GOAL_V1.md`](PRODUCT_GOAL_V1.md)의 사진과 지도, [`DECISIONS.md`](DECISIONS.md)의 open details.

### 4. 개발 환경은 지금 가진 Windows 기기와 모바일 기기로 시작하기

- **요청:** Windows 노트북과 별도 PC, AI 도구를 활용해 Android와 iOS 앱을 함께 만들고 싶다고 했다. iPhone과 iPad도 보유하고 있다고 했다.
- **이유:** 처음부터 별도 Linux 컴퓨터를 구매하는 대신 현재 장비로 앱 개발과 Android 확인을 시작하고, iOS 실기기 검증도 염두에 두려는 목적이다.
- **환경 설정 중 기록:** Windows에서 에뮬레이터가 반복 종료되고 Android Studio의 잠금 파일 접근 오류도 발생했다. SDK·임시 폴더·IDE 설정을 정리하고 에뮬레이터를 다시 구성한 뒤 Android 홈 화면과 Expo Go 연결을 확인했다. 오류별 해결 내역 대신 현재 재현 가능한 환경 설정은 설정 문서에 둔다.
- **결과:** Expo + React Native + TypeScript 방향을 정하고 Android Studio 에뮬레이터와 Expo Go로 개발을 시작했다. Obsidian은 저장소 루트를 vault로 열어 문서와 코드 계획을 한 곳에서 관리한다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Repository and client stack, [`SETUP_WINDOWS.md`](SETUP_WINDOWS.md).

### 5. 홈 화면은 ‘여행 기록’ 레이아웃, MYG 브랜드 색과 로고를 사용하기

- **요청:** 앱 레이아웃 후보 세 가지를 보고 선택하고 싶다고 했다. MYG 로고를 위쪽에 배치하고, 카카오의 노랑이나 당근의 주황처럼 앱을 떠올릴 수 있는 대표 색을 추천받아 선택한 색과 레이아웃으로 UI를 맞추길 원했다.
- **이유:** 여행과 정산 기능을 한눈에 찾을 수 있으면서, 다른 서비스와 구분되고 앱을 기억하게 할 일관된 시각 인상이 필요하다.
- **결과:** 여행 데이터가 있으면 대표 여행과 최근 지출을 먼저 보여주고, 그 아래 모임을 배치한다. 아직 여행이 없으면 첫 모임을 만들도록 안내한다. MYG 기본색은 블루 틸 `#0B7285`, 보조색은 샌드 `#F6F2E8`, 옅은 바다색 `#E3F0EF`, 코랄 `#ED8B60`으로 정했다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Visual identity.

### 6. 모임 멤버는 한 명씩 입력하고 추가하기

- **요청:** 첫 모임 만들기에서 쉼표로 여러 멤버를 한꺼번에 입력하는 방식은 불편하니, 한 명 입력 후 추가 버튼으로 목록을 만들고 싶다고 했다.
- **이유:** 입력 형식에 맞춰 쉼표를 넣거나 고치는 수고 없이, 실제 멤버 목록을 추가·확인·삭제하기 쉽도록 하려는 목적이다.
- **결과:** 멤버 한 명 입력란, 추가 동작, 현재 멤버 목록을 제공한다. 현재 UI에서는 다음 멤버를 연속해서 입력할 수 있도록 키보드 동작도 고려한다.
- **현재 기준:** 모임 생성 화면 및 [`docs/agents/roles/ux-design/ROLE.md`](agents/roles/ux-design/ROLE.md)의 폼 사용성 기준.

### 7. 여행 지역은 계층 선택과 직접 입력을 모두 지원하기

- **요청:** 전국 행정구역을 따라 내려가 지역을 고르되, 구나 동 등 어느 단계에서든 선택한 곳까지만 여행 지역으로 저장하고 싶다고 했다. 이후 지역을 직접 입력하는 방법과, 입력 후 상세 주소를 적는 칸도 요청했다.
- **이유:** 행정구역을 정확히 찾아 선택할 수 있어야 하지만, 실제 여행 목적지의 명칭이 행정구역과 다르거나 특정 장소를 바로 입력하고 싶은 경우도 있기 때문이다. 더 깊은 지역으로 탐색할 수 있게 하면서도 사용자가 도달한 단계까지만 저장할 수 있어야 한다.
- **결과:** 실제 행정구역 계층은 읍·면·동까지 탐색할 수 있고, 어느 단계의 현재 지역도 선택할 수 있다. 별도 직접 입력 모드도 제공한다. 두 방식 모두 지역을 정하면 선택 사항인 상세 주소 입력란을 보여준다.
- **후속 사용성 수정:** 동 또는 현재 행정구역을 선택하면 지역 선택 창을 닫고 상세 주소 입력란으로 포커스를 옮긴다. 키보드가 열릴 때 해당 입력란이 화면에 보이도록 스크롤한다.
- **현재 기준:** [`PRODUCT_GOAL_V1.md`](PRODUCT_GOAL_V1.md)의 모임과 여행, [`DECISIONS.md`](DECISIONS.md)의 Trip setup, 앱의 `RegionPicker`.

### 8. 여행 날짜는 캘린더에서 시작일과 종료일을 고르기

- **요청:** 여행 날짜를 직접 입력하기보다 캘린더를 열어 시작하는 날과 끝나는 날을 선택하고 싶다고 했다.
- **이유:** 날짜 형식을 직접 타이핑하거나 잘못된 종료일을 넣을 가능성을 줄이기 위해서다.
- **결과:** 시작일과 종료일을 날짜 범위 선택 UI로 정하고 종료일이 시작일보다 앞서지 않도록 한다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Trip setup.

### 9. 폼의 포커스와 키보드가 다음 동작을 방해하지 않게 하기

- **요청:** 지역 선택 후 상세 주소 칸으로 이어지지 않고 여행 이름 입력으로 돌아가는 듯한 동작을 지적했다. 이어서 화면도 입력란 쪽으로 내려와야 한다고 요청했고, 이후 모든 포커스와 입력 흐름을 사용자가 편하도록 신경 써 달라고 했다.
- **이유:** 다음에 입력할 칸을 찾으려 스크롤하거나 키보드를 반복해서 열고 닫는 행동은 여행 생성과 지출 입력을 번거롭게 한다.
- **결과:** 행정구역 선택 후 상세 주소 칸으로 자동 포커스한다. 키보드가 열릴 때 포커스된 입력란을 보이도록 스크롤하고, 이름→멤버 및 지출 내용→금액 등 연결할 수 있는 칸은 키보드의 다음 동작으로 이동한다. 날짜나 분담자처럼 텍스트가 아닌 선택을 할 때는 키보드를 닫는다.
- **앞으로의 기준:** 새 폼을 만들거나 바꿀 때 Android와 iOS 양쪽에서 포커스 순서, 키보드 종류와 완료/다음 버튼, 자동 스크롤, 키보드 닫힘, 작은 화면을 acceptance criteria에 포함한다.
- **현재 기준:** [`docs/agents/roles/ux-design/ROLE.md`](agents/roles/ux-design/ROLE.md), [`docs/agents/roles/mobile-engineering/ROLE.md`](agents/roles/mobile-engineering/ROLE.md).

### 10. AI 에이전트가 역할을 나누고 요청을 알맞은 역할로 보내기

- **요청:** 구현, 테스트, 문서화뿐 아니라 추후 UI, 서버, 마케팅 등도 AI 역할을 나누고, 메인 문서가 각 요청의 담당 역할을 정하는 harness를 만들고 싶다고 했다.
- **이유:** 같은 결정을 여러 번 설명하지 않고, AI마다 맡은 범위와 산출물을 명확하게 해 토큰과 검토 시간을 아끼려는 목적이다.
- **결과:** `docs/AI_WORKFLOW.md`를 메인 라우팅 문서로 정하고, `docs/agents/roles/<role>/ROLE.md`에 역할별 지침을 둔다. `.agents/skills/`는 구현·QA·문서화 같은 작업 절차로 계속 사용한다. 역할 폴더는 재사용 가능한 지침이며, 자동으로 AI를 실행하거나 대화 내역을 공유하지 않는다. 작은 요청은 한 역할이 끝내고, 필요한 경우에만 기획→디자인→개발→QA→문서화 순으로 넘긴다.
- **현재 기준:** [`AI_WORKFLOW.md`](AI_WORKFLOW.md), [`docs/agents/roles/`](agents/roles/).

### 11. 지출 금액은 원화로 읽기 쉽게 보이고 빠르게 더하기

- **요청:** 지출 금액을 `1,000원`처럼 원화 단위로 보기 쉽게 표시하고, `1,000원`, `5,000원`, `10,000원`, `100,000원`, `200,000원` 추가 버튼을 눌러 현재 입력값에 더하고 싶다고 했다.
- **이유:** 금액을 매번 전부 입력하는 수고를 줄이고, 큰 숫자의 자릿수를 빠르게 확인하려는 목적이다.
- **결과:** 숫자 입력은 원 단위 정수로 유지하고 화면에는 천 단위 쉼표와 `원`을 표시한다. 추가 버튼은 기존 금액에 선택한 금액을 누적한다.
- **현재 기준:** 지출 입력 화면의 결제 금액 필드.

### 12. 입력 완료 동작을 통일하고 한 달력에서 여행 기간 고르기

- **요청:** 입력 칸마다 키보드의 완료 버튼이 보이기도 하고 없기도 한 점을 정리할 수 있는지 물었다. 여행 날짜는 첨부 이미지처럼 한 달력에서 시작일과 종료일을 함께 고르고 기간이 이어진 모양으로 보이길 원했다.
- **이유:** 키보드 종류와 입력 칸에 따라 완료 동작이 달라 혼란스러울 수 있고, 시작일·종료일을 위해 달력을 두 번 여는 흐름은 날짜 범위를 한 번에 이해하기 어렵다.
- **결과:** 입력 칸은 명시적인 다음/완료 동작을 사용한다. iOS 키보드 위에는 입력 목적에 맞는 다음·추가·완료 액션을 보여주고, Android 숫자 키패드에는 입력 중 완료 버튼을 제공한다. 여행 날짜 버튼 하나에서 달력을 열어 시작일과 종료일을 고르고, 두 날짜 사이를 시각적으로 강조한 뒤 확정한다.
- **현재 기준:** [`DateRangePicker`](../src/components/DateRangePicker.tsx), [`KeyboardActionAccessory`](../src/components/KeyboardActionAccessory.tsx), [`UX design role`](agents/roles/ux-design/ROLE.md).

### 13. 앱을 다시 열어도 내 여행 기록을 보존하기

- **요청:** 휴대폰에 먼저 저장하고 나중에 서버 DB를 붙이는 단계가 맞는지 확인한 뒤, 기기 저장 방식으로 진행하기로 했다.
- **이유:** 처음에는 사용자가 직접 앱을 써 보려 하므로 앱을 재시작할 때 기록이 사라지는 문제를 먼저 없애고, 계정·초대·공유·서버 비용 결정은 여러 기기 동기화가 필요해질 때 하려는 것이다.
- **결과:** 모임·멤버·여행·지출을 기기 안의 SQLite 기반 저장소에 저장하고 시작할 때 복원한다. 앱 화면은 `GroupStore` 인터페이스를 사용해 저장 제공자와 분리했다. 저장 데이터를 읽지 못하면 빈 목록으로 덮어쓰지 않고 다시 시도 화면을 보여준다.
- **한계:** 기록은 현재 기기에만 있다. 앱을 삭제하거나 기기를 바꿔도 자동으로 옮겨지거나 친구와 공유되지 않는다. 서버로 바꿀 때는 계정·접근 권한·동기화 충돌·기존 기록 이동을 별도로 설계해야 한다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Repository and client stack, [`BUILD_PLAN.md`](BUILD_PLAN.md)의 Step 3, [`groupStore.ts`](../src/data/groupStore.ts). 저장 구현은 [Expo SDK 57 SQLite 문서](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/)를 따른다.

### 14. 하단 탭 5개와 전체 여행 기록 화면을 만들기

- **요청:** 앱 어디서든 하단에서 페이지를 이동할 수 있도록 하고, 메인 화면을 가운데 둔 5개 페이지를 원했다. 모임 목록과 전체 여행 기록을 포함하고, 기존 여행 기록 한눈보기 화면이 어색한 이유를 찾아 정리해 달라고 했다.
- **이유:** 기존 홈은 “여행 기록을 한눈에”라고 안내했지만, 선택된 모임 또는 첫 번째 모임의 여행 하나만 대표로 보여줬다. 여러 모임의 여행을 한 번에 찾거나 여행끼리 비교하기 어려웠고, 홈 요약과 목록의 역할도 겹쳤다.
- **결과:** 하단 탭을 `모임 · 여행 · 홈 · 지도 · 정산` 순서로 두고 홈을 가운데 배치했다. 홈은 모임 수·여행 수·누적 지출과 최근 여행을 요약한다. 여행 화면은 모든 모임의 여행을 시작일 순으로 모아 그룹, 인원, 지역, 기간, 지출 건수와 총액을 보여준다. 정산 화면은 지출이 있는 여행을 모으며, 지도 화면은 사진 위치 기반 지도 기능이 아직 구현 전임을 알리고 저장된 여행 지역을 보여준다. 생성·상세 화면에서는 하단 탭을 숨겨 작업 중 다른 페이지로 잘못 이동하지 않게 했다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Visual identity 및 앱의 `App.tsx`.

### 15. 지출 추가와 내역 보기를 구분하고 정산 완료 여행은 잠그기

- **요청:** `지출 기록` 버튼이 새 지출을 만드는지 기존 내역을 보는지 헷갈린다고 했다. 정산이 완료되면 더 지출을 추가할 필요가 없으므로 완료/미완료 상태를 나누고, 완료된 여행에는 지출 추가를 막아 달라고 했다.
- **이유:** 여행 상세 화면에 이미 지출 내역이 보이는데 `지출 기록`이라는 버튼은 동작을 설명하지 못했다. 또한 정산 뒤 새 지출을 넣으면 실제 송금과 계산 결과가 달라질 수 있다.
- **결과:** 입력 버튼을 `지출 추가`로 바꾸고, 지출 목록은 `지출 내역`으로 유지한다. 여행마다 정산 상태와 완료 시각을 저장하고 여행 상세·여행 목록·정산 목록에서 `정산 미완료` 또는 `정산 완료` 배지를 보여준다. 정산 결과 화면을 여는 것만으로는 완료되지 않으며 실제 송금이 끝난 후 사용자가 `정산 완료 처리`를 눌러야 한다. 완료된 여행은 지출 추가를 잠그고, `정산 다시 열기`로 잠금을 해제해 수정할 수 있다. 기존 저장 기록에 완료 시각이 없는 경우 미완료로 읽는다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Expense and settlement rules, [`models.ts`](../src/domain/models.ts), [`groupStore.ts`](../src/data/groupStore.ts), 앱의 `App.tsx`.

### 16. 홈에 최근 여행을 최대 5개 보여주고 상세 화면에서도 탭 이동 유지

- **요청:** 홈의 최근 여행 목록이 한 건뿐이니 다섯 건 정도는 보여주고, 항목을 누르면 해당 여행 상세로 들어가도록 했다. 상세 화면에 들어가면 하단 탭이 사라지는 점도 불편한지 물었다.
- **이유:** 홈에서 최근 여행을 하나씩만 열고 다시 돌아오는 일을 줄이고, 여행 상세를 확인하면서도 주요 페이지로 이동할 수 있어야 한다.
- **결과:** 홈은 시작일이 최근인 여행을 최대 5개 표시하고, 각 카드는 해당 여행 상세 화면으로 바로 연다. 모임·여행·정산 상세 화면에는 하단 탭을 유지한다. 모임/여행 생성과 지출 입력 중에는 화면 집중을 위해 탭을 숨긴다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Visual identity 및 앱의 `App.tsx`.

### 19. 사진 위 문구를 없애고 구름처럼 부드러운 페이드로 수정하기

- **요청:** 대표 이미지에 보이는 문구가 사진 자체인지 앱이 얹은 글인지 확인해 달라고 했다. 앱이 추가한 글이라면 제거하고, 사진 위아래는 뜯기거나 파먹힌 종이 모양이 아니라 구름처럼 부드럽게 흐려지도록 바꾸며, 오른쪽 위 여행 이름은 다른 글씨체로 포인트를 주길 원했다.
- **이유:** 여행 사진은 사진 자체로 감상할 수 있어야 하고, 장식 효과가 실제 사진을 잘라낸 것처럼 보이면 안 된다. 이름을 별도 필기체로 강조하면 지역 주소와 구분되면서 사진을 가리지 않는다.
- **결과:** 대표 사진 원본에는 글자가 없고 화면의 문구는 앱 오버레이였음을 확인했다. 사진 위 문구와 어두운 막을 제거하고 위아래에 종이색이 얕게 겹쳐지는 구름형 페이드를 적용했다. 여행 이름을 날짜·주소와 구분되는 필기체 포인트로 표시하고, 여행이 없을 때 생성 동작은 사진 아래로 옮겼다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Visual identity 및 앱의 `App.tsx`, 대표 이미지 `assets/jeju-editorial.png`.

### 20. 하단 네비게이션을 Travel Journal 시안에 맞추기

- **이유:** 하단 메뉴는 모든 주요 화면에서 반복되어 앱의 인상을 크게 좌우한다. 임시 문자 기호 대신 메뉴 의미를 바로 알아볼 수 있는 통일된 아이콘이 필요하다.
- **결과:** 문자 기호를 사람·여행 가방·집·접힌 지도·정산 내역의 선 아이콘으로 교체하고, 홈 선택 상태는 러스트색 채움으로 표현한다. 바탕을 종이색 표면으로 맞추고 위쪽 구분선을 얇게 해 참고 이미지에 가까운 높이와 여백으로 조정한다.

### 21. 여행 시작·종료와 위치 사진 지도를 추가하기

- **요청:** 여행을 직접 시작하고 종료하는 처리, 여행 사진을 추가해 위치와 함께 지도에서 보는 기능을 개발해 달라고 했다. 로그인도 필요하며 Google·Kakao·Naver·이메일 계정 가입이 가능한지 확인해 달라고 했다.
- **이유:** 여행 일정만 등록하는 데서 그치지 않고 실제 여행 중의 기록을 남기려면 시작/종료 상태와 사진 위치가 필요하다. 계정/인증은 친구 간 공유와 데이터 동기화의 기반이므로 서버 선택이 선행되어야 한다.
- **결과:** 여행에 시작·종료 시각을 저장하고 준비/여행 중/종료 상태를 보여준다. 여행 상세에서 사진을 여러 장 골라 앱 내부 저장소에 복사하며, 사진에 GPS EXIF가 있으면 좌표를 저장하고 추억 지도에 핀을 표시한다. 위치 없는 사진은 여행 사진에는 보존하되 지도에 추정 좌표를 만들지 않는다. 사진과 지도는 현재 기기 로컬로 동작한다. 인증은 서버 선택을 기다리는 중이며 Google과 Kakao, Naver 연동 및 이메일 확인 방식의 검토 결과를 아래 출처에 기록한다.
- **공식 참고:** Expo의 [`expo-image-picker`](https://docs.expo.dev/versions/latest/sdk/imagepicker/)는 Android/iOS에서 EXIF를 제공하지만 iOS에서는 경우에 따라 GPS 태그가 없을 수 있다. [`react-native-maps`](https://docs.expo.dev/versions/latest/sdk/map-view/)는 Expo Go에서 테스트할 수 있다. Supabase는 [`이메일·비밀번호 및 이메일 확인`](https://supabase.com/docs/guides/auth/passwords), [`Google/Kakao 등 소셜 로그인`](https://supabase.com/docs/guides/auth/social-login), 그리고 [`사용자 정의 OAuth/OIDC 제공자`](https://supabase.com/docs/guides/auth/custom-oauth-providers)를 문서화한다.
- **현재 기준:** 앱의 `App.tsx`, `src/domain/models.ts`, `src/domain/tripLifecycle.ts`, `src/domain/photoLocation.ts`, `src/components/TripPhotos.tsx`; 인증 서비스는 미결정.

### 23. `모여고`를 로고답게 보이게 하고 홈 사진을 여행별로 연결하기

- **요청:** `모여고` 글자만 있으면 일반 문장처럼 보여 로고 느낌을 더하고 싶다고 했다. 여행마다 사진을 따로 둘 수 있는지, 홈 대표 사진이 최신 여행 사진인지, 사진이 없을 때 무엇을 보여줄지도 확인해 달라고 했다.
- **이유:** 워드마크에 알아보기 쉬운 상징이 있어야 앱의 이름이 브랜드로 읽힌다. 홈 사진은 실제 여행 기록과 이어져야 하고, 사진이 없을 때 다른 여행의 사진을 임의로 보여주면 기록을 혼동할 수 있다.
- **결과:** 세 지점이 여행 경로로 이어지는 심볼과 `모여고` 워드마크를 조합한다. 각 여행은 기존처럼 자신의 사진 목록을 보유한다. 이 단계에서는 홈에 여행 사진과 종이 지도 기본 표지를 연결했다.
- **정산 후 멤버 확인 제안(미결정):** 총무가 정산 요청을 시작하고, 각 멤버에게 자신이 보내야 할 금액과 받을 사람을 알려준다. 송금할 금액이 있는 멤버가 외부 송금을 마친 뒤 앱에서 완료를 표시하며, 필요한 송금이 모두 표시되면 여행을 완료 상태로 전환하는 흐름을 검토한다. 은행 이체를 자동 확인하는 기능은 포함하지 않는다. 실제 개인별 알림에는 멤버를 앱 계정에 연결하는 초대·가입 흐름, 서버 저장, 푸시 알림 설정이 필요하다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Visual identity 및 앱의 `App.tsx`, `Trip.photos`. 정산 요청·멤버별 확인·자동 완료는 서버와 계정 방식을 정한 뒤 확정한다.

### 24. 사진이 없을 때 예시 이미지를 숨기고 대표 사진을 여행별로 선택하기

- **요청:** 사진을 추가하지 않은 여행에도 예시 이미지가 보이는 문제를 없애 달라고 했다. 여행별 대표 사진을 지정하면 해당 사진을 사용하고, 대표를 지정하지 않은 경우 처음 등록한 사진을 보여 달라고 했다.
- **이유:** 예시 사진을 실제 여행 사진으로 오해하지 않도록 하고, 여행마다 사용자가 선택한 추억 사진을 대표 이미지로 보여줘야 한다.
- **결과:** 홈과 최근 여행 목록에서 고정 예시 이미지를 제거한다. 사진이 있는 여행은 대표로 지정한 사진을 우선 표시하고, 대표 설정이 없으면 첫 등록 사진을 쓴다. 사진이 없는 여행은 이미지와 썸네일을 숨긴다. 여행 사진 목록에서 각 사진을 대표로 설정할 수 있으며, 대표 사진을 삭제하면 남은 사진 중 첫 사진으로 돌아간다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Visual identity와 `Trip.coverPhotoId`, `Trip.photos` 구현.

### 25. 기본 표지를 다시 사용하고 홈 여행 목록의 제목을 강조하기

- **요청:** 사진이 없는 여행에 모여고 기본 표지를 사용하는 편이 좋다고 결정했다. 같은 기본 이미지로 통일하고, 홈 최근 여행 목록에서 주소보다 여행 제목을 크게 표시해 달라고 했다.
- **이유:** 사진이 없는 행의 빈 공간보다 서비스 고유의 표지가 목록을 더 자연스럽게 연결한다. 여행 이름을 먼저 읽게 하면 지역 주소와 기록 제목의 역할이 분명해진다.
- **결과:** 홈 대표 영역과 최근 여행 썸네일은 같은 기본 표지를 사용한다. 사진이 있으면 지정 대표 사진, 지정이 없으면 첫 등록 사진을 사용한다. 최근 여행 목록에서 여행 제목은 크게, 지역과 상세 주소는 보조 글씨로 표시한다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Visual identity 및 앱의 `App.tsx`.

### 26. 사진이 없는 여행마다 5가지 기본 표지를 순서대로 사용하기

- **요청:** 기본 표지 5개를 쓰되 사진이 없는 여행 순서에 따라 2 → 1 → 3 → 4 → 5번을 보여 달라고 했다. 실제 사진이 있는 여행은 기본 표지 순서에서 건너뛴다.
- **이유:** 같은 기본 이미지가 여러 번 반복되는 인상을 줄이고, 사진이 없는 여행 카드마다 서로 다른 분위기를 주기 위해서다.
- **결과:** 다섯 표지 이미지를 앱 에셋으로 추가하고, 사진이 없는 여행에만 2, 1, 3, 4, 5 순으로 배정한다. 실제 사진이 있는 여행은 지정 대표 사진 또는 첫 등록 사진을 사용하며 기본 표지 순번을 소비하지 않는다. 다섯 장을 모두 사용한 뒤에는 순서를 반복한다. 홈 대표 영역과 최근 여행 목록이 같은 계산 규칙을 사용한다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Visual identity, `src/domain/tripCoverPhoto.ts`, `src/components/TripFallbackCover.tsx`.

### 27. 이미 만든 여행의 정보를 수정하기

- **결과:** 여행 상세 화면에 `수정` 버튼을 두고 여행 이름, 지역, 상세 주소, 날짜, 총무를 기존 값이 채워진 편집 화면에서 변경할 수 있게 한다. 저장할 때 지출, 사진, 대표 사진, 시작·종료 상태와 정산 완료 기록을 유지한다.

### 28. 지출 내역에 자주 쓰는 항목 버튼 추가하기

- **이유:** 매번 같은 지출명을 키보드로 입력하는 수고를 줄여 여행 중 빠르게 기록할 수 있어야 한다.
- **결과:** 지출 입력 화면에서 `무엇을 결제했나요?` 입력칸을 먼저 보여주고 바로 아래에 점심 식사, 저녁 식사, 숙소비, 교통비, 카페·간식 버튼을 둔다. 버튼은 내역 입력칸에 제목을 채우고, 사용자는 그 제목을 직접 수정할 수 있다. 금액·결제자·분담 멤버 선택은 기존 흐름을 그대로 사용한다.

### 29. 지출 내역을 수정하거나 삭제하기

- **요청:** 저장한 지출의 입력 내용을 고치거나 잘못 등록한 지출을 삭제할 수 있도록 해 달라고 했다.
- **이유:** 금액·결제자·분담 인원 입력 실수를 바로잡기 위해 같은 여행에 지출을 다시 만들 필요가 없어야 하며, 삭제한 기록이 정산 결과에도 반영되어야 한다.
- **결과:** 여행 상세의 각 지출에 `수정`과 `삭제` 동작을 제공한다. 수정 화면은 기존 내역·금액·결제자·분담 멤버를 불러오고 저장 시 같은 지출을 교체한다. 삭제는 확인을 거친 뒤 해당 기록만 제거한다. 두 동작 모두 현재 지출 목록을 기준으로 정산을 다시 계산하며, 정산 완료 상태에서는 정산을 다시 열어야 수정·삭제할 수 있다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Expense and settlement rules 및 앱의 `App.tsx`, `src/domain/expenseEditing.ts`.

### 30. 정산 완료 처리 버튼을 더 잘 보이게 하기

### 31. 정산 요청을 멤버에게 보내고 송금 확인을 모으기

- **요청:** 총무가 정산 요청을 만들면 멤버에게 알림을 보내고, 각 멤버의 송금 완료 확인이 모이면 여행을 완료 처리하고 싶다고 했다. 로그인 기능이 먼저 필요한지도 물었다.
- **이유:** 현재 정산 결과는 이 기기의 기록에만 있어 다른 사람에게 전달하거나 각자의 송금 확인을 모을 수 없다.
- **결과:** 정산 요청, 돈을 보내야 하는 멤버의 완료 표시, 모든 필요한 송금 확인 후 자동 정산 완료를 승인된 동작으로 기록했다. 알림은 로그인만으로 충분하지 않다. 각 멤버 계정 연결, 기기 간 공유 서버와 권한 검사, 푸시 토큰 등록 및 서버 발송이 필요하다. 현재 저장 방식은 기기 로컬이므로 실제 멤버 알림 구현은 백엔드 선택 후 진행한다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Expense and settlement rules. 현재 앱은 로컬 저장만 사용하며, 서버와 인증 제공자는 아직 선택되지 않았다.

### 32. 계정·멤버 연결과 접근 권한을 먼저 설계하기

- **요청:** 로그인·공유 서버·푸시 알림보다 먼저 무엇을 정할지 안내한 뒤, 계정과 모임 멤버 연결, 초대, 접근 권한 설계부터 진행해 달라고 했다.
- **이유:** 이름만 저장되는 로컬 멤버를 실제 계정과 안전하게 연결하지 않으면 다른 기기 공유와 개인별 정산 알림을 정확히 전달할 수 없다.
- **결과:** 계정/모임/멤버/초대/여행/지출/사진/정산/기기 알림 데이터의 초안, 접근 권한 매트릭스, 초대·계정 연결 흐름, 기존 기기 데이터 이전 경로를 [`ACCOUNT_MEMBERSHIP_ACCESS_DESIGN.md`](ACCOUNT_MEMBERSHIP_ACCESS_DESIGN.md)에 정리했다. Supabase는 추천 후보로만 적었고 제공자와 열린 제품 선택은 미승인 상태로 남겼다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Open product and technical details와 설계 초안. 백엔드 프로젝트 생성이나 인증·푸시 구현은 아직 하지 않았다.

### 33. Supabase 데이터베이스와 이메일·Google·Kakao 계정 준비하기

- **요청:** 다음 작업으로 데이터베이스/접근 정책과 계정 로그인을 진행하되, Naver는 우선 제외하기로 했다.
- **이유:** 다른 기기에서 모임 데이터를 공유하고 정산 요청을 멤버에게 보내려면, 로그인 계정과 모임 멤버를 안전하게 연결할 서버 기반이 필요하다.
- **결과:** Supabase를 계정 및 공유 데이터 기반으로 선택했다. 앱에는 이메일 가입/로그인, 확인 메일 딥 링크 처리, Google/Kakao 브라우저 OAuth, 로그아웃, 계정 화면을 추가했다. 초기 Postgres 스키마와 RLS 정책, 일회용 멤버 지정 초대 RPC 및 정산 입력 변경 시 pending 요청 무효화 트리거를 준비했다. 설정 순서는 [`SUPABASE_SETUP.md`](SUPABASE_SETUP.md)에 기록했다. Naver는 제외했다.
- **범위/검증:** 앱 키가 아직 연결되지 않아 실제 계정 제공자 왕복 로그인은 검증하지 않았다. 현재 앱은 계속 로컬 저장을 사용하며 서버 동기화, 기존 데이터 이전, 초대 UI, 사진 업로드와 푸시 알림은 다음 작업이다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Repository and client stack 및 [`ACCOUNT_MEMBERSHIP_ACCESS_DESIGN.md`](ACCOUNT_MEMBERSHIP_ACCESS_DESIGN.md). 구현은 `src/data/supabase.ts`, `App.tsx`, `supabase/migrations/202610100001_initial_schema.sql`.

### 34. 로그인 전 앱 페이지를 잠그고 기존 기록 보존하기

- **요청:** 로그인하지 않은 사용자는 앱 페이지에 들어갈 수 없게 하고, 로그인에 성공한 뒤에만 앱을 열도록 요청했다. 로그인 과정에서 기존 여행 기록이 사라질까 걱정했다.
- **이유:** 계정 화면만 제공하는 것보다 앱 진입부터 인증 상태를 일관되게 적용하고, 기존 기기 기록이 로그인 때문에 초기화되는 오해를 막아야 한다.
- **결과:** Supabase 인증 상태 확인 중에는 로딩 화면을, 로그아웃 상태에는 로그인/가입 화면을 표시하고, 로그인된 경우에만 기존 앱 페이지를 연다. 로컬 SQLite 데이터를 삭제하거나 비우는 로직은 추가하지 않았다.
- **범위:** 기존 기록은 계속 기기에 저장된다. 로그인만으로 서버 계정에 기록이 귀속되거나 다른 기기와 동기화되지는 않는다. 계정별 서버 데이터 연결과 안전한 로컬 이전은 별도 작업으로 남는다. Supabase 설정이 아직 없으므로 실제 계정으로 잠금 해제하는 검증은 설정 후 가능하다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Repository and client stack 및 [`SUPABASE_SETUP.md`](SUPABASE_SETUP.md). 구현은 `App.tsx` 인증 상태 게이트와 `src/data/supabase.ts`.

### 35. 로그인 화면은 모여고 디자인을 유지하고 로그인 방식만 단순하게 보여주기

- **요청:** 참고 이미지에서는 로그인 방식의 배치만 참고하고, 모여고의 디자인은 유지해 달라고 했다. 로그인은 카카오, Google, 이메일 로그인/회원가입만 제공한다.
- **이유:** 기존에는 이메일 입력 폼과 소셜 로그인 버튼이 한 화면에 함께 있어 일반 앱의 시작 화면처럼 간단히 읽히지 않았다. 참고 앱의 브랜딩을 가져오지 않고, 익숙한 로그인 방식 배치만 적용한다.
- **결과:** 참고 이미지의 최신 지정에 맞춰 로그인 화면에 이메일·비밀번호 입력과 로그인 버튼을 먼저 두고, 그 아래에서 회원가입으로 전환하도록 한다. 하단의 카카오와 Google 로그인은 각 행이 화면 너비를 채우는 가로형 버튼 두 개로 세로 배치한다. 카카오 버튼은 노란색, Google 버튼은 밝은 종이색으로 구분하고 제공자 표식은 왼쪽에 둔다. 모여고의 종이색 배경, 편집체 제목, 기존 색과 로고는 유지하고 참고 앱의 브랜드 디자인은 가져오지 않는다. Naver와 비밀번호 찾기는 로그인 방식 범위에 포함하지 않는다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Repository and client stack 및 `App.tsx` 인증 화면.

### 36. 이메일 도메인 선택과 3분 인증번호 가입

- **요청:** 이메일 아이디 뒤의 `@` 도메인을 기본 목록에서 고르거나 직접 입력하고, 가입 확인은 3분 안에 인증번호를 입력하게 해 달라고 했다. 시간이 지나면 다시 발급해 남은 시간을 새로 시작하고, 번호 입력도 다시 시도할 수 있어야 한다.
- **이유:** 모바일에서 전체 이메일을 매번 입력하는 수고를 줄이고, 가입 확인을 앱 안에서 끝내며 인증번호 만료와 재전송 상태를 분명하게 보여주기 위해서다.
- **결과:** 가입 화면은 아이디 부분과 고정 `@`를 분리하고 Gmail, Naver, Daum, Hanmail, Outlook 도메인 또는 직접 입력 도메인을 지원한다. 가입 후 인증번호 화면은 남은 시간을 3분 카운트다운으로 표시하고, 60초 재전송 대기 후 새 번호를 보내며 타이머를 다시 시작한다. 인증 실패는 입력을 유지해 재시도할 수 있고, 이메일 수정으로 가입 폼에 돌아갈 수 있다. Supabase Auth의 실제 만료 시간과 메일 템플릿은 프로젝트 대시보드에서 별도로 `180`초 및 `{{ .Token }}`으로 맞춰야 한다.
- **범위/검증:** 앱 코드에서 가입·확인·재전송 흐름을 구현하고 타입 검사를 한다. 실제 메일 전송과 3분 만료는 Supabase 설정 및 SMTP에 의존하므로 설정 적용 후 기기에서 확인한다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 이메일 계정 동작 및 [`SUPABASE_SETUP.md`](SUPABASE_SETUP.md)의 인증번호 설정 순서. 구현은 `App.tsx`.

### 37. 회원가입 비밀번호 규칙과 확인 입력

- **요청:** 회원가입 시 비밀번호에 최소 길이와 대문자·특수문자 포함 규칙을 적용하고, 확인 입력으로 오타를 막아 달라고 했다.
- **이유:** 가입 단계에서 필요한 기준을 미리 보여주고, 입력 실수로 나중에 로그인이 안 되는 상황을 줄인다.
- **결과:** 회원가입 화면은 비밀번호 8자 이상, 영문 대문자 1개 이상, Supabase가 허용하는 특수문자 1개 이상을 실시간으로 표시한다. 비밀번호 확인 칸이 원문과 일치해야 제출할 수 있고, 조건 미충족/불일치 시 명확한 안내를 보여준다. 로그인 화면에는 이 가입 전용 확인 칸과 복잡도 검사를 적용하지 않는다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 계정 인증 규칙 및 `src/domain/passwordPolicy.ts`. Supabase Auth는 별도 프로젝트 설정으로 최소 길이와 지원하는 문자군을 강제할 수 있다.

### 38. 회원가입에서 입력 포커스와 키보드 스크롤 연결

- **요청:** 이름, 이메일 아이디를 입력한 뒤 도메인을 고르면 다음 입력칸으로 커서가 이동하고, 화면도 해당 입력칸이 보이도록 함께 내려가야 한다.
- **이유:** 모바일 키보드가 다음 입력칸을 가리거나 사용자가 화면을 직접 찾느라 가입 흐름이 끊기지 않게 한다.
- **결과:** 이름 입력 완료 시 이메일 아이디에 포커스한다. 이메일 도메인 선택 후 일반 도메인은 비밀번호로, 직접 입력 도메인은 도메인 입력칸으로 이동한다. 직접 입력 도메인 입력 완료 시 비밀번호로, 비밀번호 입력 완료 시 확인 입력칸으로 이어진다. 포커스된 입력칸은 키보드 위로 스크롤한다.

### 41. 인증번호 메일을 위해 Resend SMTP 연결

- **요청:** Supabase 가입 확인 메일이 기본 링크 형식으로 도착하자, 앱에서 입력할 6자리 인증번호 메일을 설정하려고 했다.
- **이유:** 새 Supabase Free 프로젝트는 기본 SMTP를 쓸 때 인증 메일 템플릿을 편집할 수 없어서 앱의 OTP 입력 흐름과 기본 링크 메일이 맞지 않는다.
- **결과:** 초기 인증 메일 발송용 SMTP로 Resend를 선택했다. Supabase SMTP 설정에 Resend 자격 증명을 넣은 뒤 Confirm signup 템플릿을 `{{ .Token }}`을 포함한 6자리 코드 형식으로 바꾸고, OTP 만료를 180초로 맞춘다. 도메인 인증 전에는 발신 가능한 주소가 제한될 수 있다.
- **현재 기준:** [`SUPABASE_SETUP.md`](SUPABASE_SETUP.md)와 [`DECISIONS.md`](DECISIONS.md)의 계정 설정. SMTP 저장만으로 메일 템플릿은 바뀌지 않으므로 템플릿 저장 후 새 가입 또는 재전송으로 확인한다.

### 42. 중복 가입과 미인증 계정 상태를 분명하게 처리

- **요청:** 이미 계정이 있으면 새 가입으로 안내하지 말고, 이메일 인증 전에는 실제 앱 사용자로 취급하지 말아 달라고 했다. 이메일 발송도 확인하고, Resend 설정이 문제면 수정해 달라고 했다.
- **확인:** Supabase Users 화면의 기존 계정은 `Confirmed at` 시간이 있는 인증 완료 계정이었다. 직전 `/signup` 로그는 `user_repeated_signup`으로 기록되어 새 인증 메일을 보낸 가입이 아니었다. Resend의 Emails 화면은 발송 내역이 없었고 Domains 화면에도 검증된 도메인이 없었다. Supabase 이메일 설정은 8자리·3600초였으므로 앱 기준인 6자리·180초로 저장했다.
- **이유:** Supabase는 가입 인증 대기 중인 Auth 행을 확인 전부터 만들고, 확인 완료 전에는 로그인 세션을 주지 않는다. 기존 확인 완료 계정의 중복 가입 응답은 계정 열거 방지를 위해 가려질 수 있어 앱이 이를 정상 새 가입처럼 보이면 사용자는 메일이 발송됐다고 오해한다.
- **결과:** 앱은 빈 identities를 가진 중복 가입 응답을 감지해 OTP 화면으로 가지 않고 로그인 화면으로 안내한다. 세션을 복구하거나 갱신할 때도 이메일 확인 완료 전에는 앱 페이지를 열지 않는다. 가입 화면은 이메일 확인이 로그인에 필요함을 알려준다. Resend는 도메인이 없어 일반 수신자에 대한 실제 인증 메일 발송을 검증할 수 없으며, 사용자가 보유한 도메인과 DNS 검증이 필요하다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md), [`SUPABASE_SETUP.md`](SUPABASE_SETUP.md), `App.tsx`, `src/domain/authSignup.ts`.
- **후속 설정:** 사용자가 API 키 생성을 승인해 Resend에 Sending access 키를 만들고 Supabase SMTP Password에 저장했으며, Username은 `resend`로 저장했다. 키 자체는 문서에 남기지 않는다. 사용자가 `moyeogo.kr`을 선택해 Resend에 도메인으로 추가하고 Supabase Sender email은 `noreply@moyeogo.kr`로 저장했다. Resend가 안내한 DNS 레코드는 아직 도메인 제공자에 등록하지 않아 도메인 검증과 앱 OTP 수신 확인은 미완료다. Resend onboarding의 테스트 발송도 비활성화되어 Emails에 발송 결과가 생기지 않았다.

### 43. Google OAuth가 localhost 오류로 끝나는 문제 조사

- **요청:** Google 로그인을 직접 확인하고, 인증 후 `localhost`에서 사이트에 접근할 수 없다는 오류가 나는 원인을 찾아 고쳐 달라고 했다.
- **확인:** Android 에뮬레이터에서 Google 계정 인증과 Supabase OAuth 콜백은 성공했지만, 브라우저가 `http://localhost:3000`으로 이동해 연결 거부 화면을 보였다. Expo Go에서 앱이 요청한 콜백은 `exp://192.168.75.158:8083/--/auth/callback`이었다. Supabase Redirect URLs에 이 Expo 주소들과 `moyeogo://auth/callback`을 추가했다.
- **이유:** Google 자격 증명 검증은 통과했으므로 실패 구간은 Google 로그인 자체가 아니라 Supabase에서 앱으로 돌아오는 리디렉션이다. 안정적인 앱 콜백 주소를 확인하기 위해 `expo-dev-client`를 설치하고 Android 개발 빌드를 준비했다.
- **결과:** 최초 시도에서는 Supabase의 Site URL이 `http://localhost:3000`이라 기본 주소로 돌아갔다. 사용자가 승인해 Site URL을 Expo Go 콜백 `exp://192.168.75.158:8083/--/auth/callback`으로 변경했고, 허용 Redirect URLs에도 동일 주소가 남아 있다. 8083 포트에서 이 프로젝트의 Expo 서버가 실행 중임을 확인했다. 사용자는 재로그인 후 로그인된 것 같다고 보고했다. 별도 네이티브 개발 빌드는 아직 필요하지 않아 성공 여부의 추가 확인은 앱 홈 진입/세션 유지로 이어간다.

### 44. 계정마다 여행 기록을 분리하고 새 계정은 빈 기록으로 시작

- **요청:** 첫 Google 로그인을 했는데 기존 기록이 보이는 이유를 물었고, 새 계정은 빈 기록으로 시작하며 계정마다 등록된 기록이 달라야 한다고 명확히 요청했다.
- **이유:** 기존 앱은 모든 모임·여행·지출을 기기 하나의 SQLite 키에 저장했으므로, 어떤 계정으로 로그인해도 같은 기록이 표시됐다.
- **결과:** Supabase 사용자 ID별로 별도 기기 저장 키를 사용한다. 새 계정은 빈 목록으로 시작하고, 다른 계정으로 바꾸면 그 계정의 저장 기록만 불러온다. 로그인 전에 있던 기존 기록은 삭제하거나 첫 계정에 자동 귀속하지 않고 원래 키에 보존한다. 계정별 기록은 아직 이 기기에만 저장되며, 같은 계정의 다른 기기 동기화와 기존 기록 가져오기는 후속 작업이다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Repository and client stack, [`ACCOUNT_MEMBERSHIP_ACCESS_DESIGN.md`](ACCOUNT_MEMBERSHIP_ACCESS_DESIGN.md), `src/data/groupStore.ts`, `App.tsx`.

### 46. 모임 생성 시 본인 닉네임을 멤버로 자동 포함

- **요청:** 모임을 만드는 사용자도 직접 멤버로 입력해야 하는 점을 고치고, 본인은 계정 닉네임으로 자동 추가해 달라고 했다. 앱 가입 친구는 친구 요청/목록 또는 친구 ID 검색으로 찾고, 목록에서 모임에 초대하거나 공유한 초대 코드를 입력해 들어오도록 하며, 비회원은 지금처럼 이름으로 등록하길 원했다.
- **이유:** 만든 사람을 다시 입력하는 수고와 누락을 없애고, 모임 멤버를 앱 계정과 비회원으로 구분할 기반을 만든다.
- **결과:** 현재 로그인 계정의 닉네임을 미리 채우는 입력란을 두고, 모임 생성 시 본인을 첫 멤버로 자동 포함한다. 친구 ID 검색, 친구 요청/수락, 친구 목록에서 초대, 공유 초대 코드, 비회원 등록을 함께 지원하는 방향을 정했다. 초대받은 계정에 여행과 지출 데이터를 보여주려면 원격 모임 동기화도 연결해야 하므로 친구 초대 UI는 그 구현과 함께 진행한다.
- **현재 기준:** [`DECISIONS.md`](DECISIONS.md)의 Product scope, [`ACCOUNT_MEMBERSHIP_ACCESS_DESIGN.md`](ACCOUNT_MEMBERSHIP_ACCESS_DESIGN.md), `App.tsx`, `src/domain/groupCreation.ts`.

### 47. 고유 닉네임, 친구 관리, 계정 설정

- **요청:** Google·Kakao 로그인 뒤 사용할 닉네임을 선택하고, 중복 닉네임을 막으며, 친구 관리 화면과 계정 설정의 닉네임 변경·알림 허용 기능을 추가해 달라고 했다.
- **이유:** 친구 연결은 이메일이나 동명이인에 기대지 않고 고유 식별자로 안전하게 관리해야 하며, 새 계정도 앱에서 불릴 이름을 직접 선택해야 한다.
- **결과:** 로그인 직후 닉네임이 없는 계정은 등록을 마칠 때까지 앱 화면에 진입하지 못한다. 계정 설정에서 닉네임을 바꾸고, 서버의 대소문자 구분 없는 고유 인덱스로 중복을 거절한다. 각 계정에는 `MG-XXXXXXXX` 형식의 친구 ID가 있고, 친구 관리 화면에서 ID 검색, 요청 보내기, 받은 요청 수락·거절, 친구 목록 확인을 제공한다. 계정의 앱 알림 수신 선호도도 저장한다. 푸시 권한·토큰과 실제 알림 발송, 친구를 모임에 초대하는 기능은 아직 연결하지 않았다.

### 72. 초대받은 계정은 수락한 뒤 모임 멤버로 반영

- **요청:** 모임 생성자는 생성 즉시 멤버가 되고, 계정 초대를 받은 회원은 초대를 수락한 뒤 모임 목록과 멤버십에 반영되며, 비회원은 기존처럼 게스트로 다루도록 요청했다.
- **이유:** 계정 데이터가 기기 간 동기화되지 않아 초대를 수락하기 전부터 다른 계정의 모임이나 멤버십으로 취급할 수 없다.
- **결과/현재 범위:** 생성자는 즉시 활성 멤버가 된다. 초대받은 계정은 수락 전 모임 목록과 멤버십에서 제외되고, 수락 후 두 곳에 반영된다. 계정이 없는 사람은 이름 기반 게스트로 유지한다. 백엔드 스냅샷 저장·초대 API와 migration 파일이 준비됐고 프론트 연결 코드는 작성 완료되어 정적 검사를 통과했다. DB migration은 아직 적용되지 않았고 기기 간 실사용 검증도 완료되지 않아 전체 흐름은 아직 검증되지 않았다.

### 74. 모임 삭제·탈퇴와 생성자 알림을 서버 계약으로 추가

- **요청:** 생성자만 가능한 영구 모임 삭제, 앱 계정 초대 수락 전 pending 상태와 게스트 active 상태 보존, 앱 계정 멤버의 자진 탈퇴, 생성자에게 저장되어 조회 가능한 알림을 요청했다.
- **이유:** 기존 원격 모임 스냅샷·초대 기반 위에 서버가 주체와 권한을 확인하는 수명주기 처리가 필요하다.
- **결과:** `delete_remote_group`은 생성자만 호출할 수 있고 여행 및 종속 기록을 함께 영구 삭제한다. `leave_remote_group`은 활성 비생성자 계정 멤버만 허용하며 멤버 행은 과거 참조 보존을 위해 남긴다. 탈퇴와 생성자 대상 `member_left` 알림 저장은 하나의 트랜잭션이다. `list_my_group_notifications`는 현재 계정에 저장된 알림을 최신순으로 반환한다. 읽음 처리와 푸시 발송은 추가하지 않았다. 기존 invitation RPC는 초대 계정을 pending으로 두고 수락 후 active로 바꾸며, 게스트는 active로 저장한다. 모임 조회 응답은 멤버 ID별 `memberStatuses`를 포함해 생성자가 pending 초대를 구분할 수 있다.
- **근거:** [`DECISIONS.md`](DECISIONS.md), [`202610170001_remote_group_lifecycle_and_notifications.sql`](../supabase/migrations/202610170001_remote_group_lifecycle_and_notifications.sql), [`remoteGroups.ts`](../src/data/remoteGroups.ts). DB migration 미적용 상태이며 실제 원격 실행은 확인하지 않았다.

### 75. 원격 모임 마이그레이션을 Supabase에 적용
